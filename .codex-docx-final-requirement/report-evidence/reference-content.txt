P0002 [Normal] Final Requirement
P0003 [Normal] 1. ขอบเขตของระบบ
P0004 [Normal] Online Leave Approval System เป็นระบบสำหรับบริหารจัดการกระบวนการลาของบุคลากรภายในองค์กร ตั้งแต่การเข้าสู่ระบบ การสร้างและส่งคำขอลา การตรวจสอบสิทธิ์การลาและวันลาคงเหลือ การคำนวณวันทำงาน การอนุมัติหรือปฏิเสธคำขอ การติดตามสถานะ และการแจ้งเตือนภายในระบบ
P0005 [Normal] ระบบรองรับการจัดการข้อมูล Employee, Leave Type, Leave Entitlement และ Holiday สำหรับฝ่ายทรัพยากรบุคคล ตลอดจนการจัดการ User Account, Department, Position และ Audit Log สำหรับผู้ดูแลระบบ รวมถึง Dashboard และรายงานตามขอบเขตของแต่ละ Role ข้อมูลธุรกิจหลักถูกจัดเก็บในระบบกลางเพื่อให้การแสดงผลและการทำงานของแต่ละส่วนมีความสอดคล้องกัน
P0006 [Normal] ระบบมีผู้ใช้งาน 4 Role ได้แก่ Employee, Supervisor, HR และ Admin โดยผู้ใช้งานทุก Role สามารถใช้ความสามารถด้านคำขอลาของตนเองตามเงื่อนไขที่กำหนด Workflow การอนุมัติปัจจุบันเป็นการอนุมัติขั้นเดียว ผู้ใช้งานส่ง Leave Request ให้ Supervisor ซึ่งเป็นหัวหน้างานโดยตรงพิจารณาและเปลี่ยนผลเป็น Approved หรือ Rejected

  R002 | Supervisor | ใช้ความสามารถด้านการลาของตนเอง พิจารณาคำขอของพนักงานที่อยู่ภายใต้การดูแลโดยตรง และดู Team Report

P0022 [Normal] 5. Business Rule
T003 BLOCK=23 ROWS=38 GRID=[1200, 8150]
  R000 | รหัส | Business Rule
  R001 | BR-01 | การ Submit ต้องระบุ Leave Type, Start Date, End Date และ Reason ครบถ้วน
  R002 | BR-02 | End Date ต้องไม่ก่อน Start Date และวันที่ต้องอยู่ในรูปแบบที่ระบบยอมรับ
  R003 | BR-03 | Leave Request หนึ่งรายการต้องไม่ข้ามปี
  R004 | BR-04 | Reason ต้องมีความยาวตั้งแต่ 5 ถึง 500 ตัวอักษร
  R005 | BR-05 | Submit ได้เฉพาะ Leave Type ที่ Active
  R006 | BR-06 | Working Days ไม่นับวันเสาร์ วันอาทิตย์ และ Holiday ที่ Active
  R007 | BR-07 | ช่วงวันที่ที่ไม่มี Working Day ไม่สามารถ Submit ได้
  R008 | BR-08 | จำนวนวันลาต้องอยู่ระหว่าง Minimum Days และ Maximum Days Per Request ของ Leave Type
  R009 | BR-09 | ผู้ยื่นต้องมี Leave Entitlement ของ Employee, Leave Type และปีที่เลือก
  R010 | BR-10 | Leave Balance ที่ใช้ยื่นคำขอคำนวณจาก Total ลบ Used และ Pending
  R011 | BR-11 | Pending Request ของประเภทและปีเดียวกันต้องถูกนำไปหักออกจาก Leave Balance ที่ใช้ได้
  R012 | BR-12 | ห้ามช่วงวันลาทับกับ Leave Request สถานะ Pending หรือ Approved ของ Employee คนเดียวกัน
  R013 | BR-13 | เมื่อ Leave Type กำหนดให้แนบเอกสารและถึง Threshold ผู้ยื่นต้องมี Attachment ก่อน Submit
  R014 | BR-14 | Attachment รองรับ PDF, JPEG และ PNG สูงสุด 5 ไฟล์ โดยแต่ละไฟล์ไม่เกิน 10 MB
  R015 | BR-15 | ดาวน์โหลด Attachment ได้เฉพาะเจ้าของ Direct Supervisor, HR หรือ Admin
  R016 | BR-16 | แก้ไขหรือลบ Leave Request และลบ Attachment ได้เฉพาะรายการที่เป็น Owned Draft
  R017 | BR-17 | เจ้าของยกเลิกได้เฉพาะ Leave Request สถานะ Pending
  R018 | BR-18 | Submit ต้องพบ Supervisor ที่ผูกกับ Employee และ Supervisor ต้องมี User Account
  R019 | BR-19 | เฉพาะ Role Supervisor เท่านั้นที่ใช้ Approval Function ได้ และคำขอต้องเป็นของ Direct Team
  R020 | BR-20 | Supervisor ห้าม Approve หรือ Reject Leave Request ของตนเอง
  R021 | BR-21 | Approve หรือ Reject ทำได้เฉพาะสถานะ Pending และคำขอที่ตัดสินแล้วไม่สามารถตัดสินซ้ำ
  R022 | BR-22 | Reject ต้องระบุ Rejection Reason
  R023 | BR-23 | Approve ต้องตรวจ Entitlement และ Balance ซ้ำภายใน Transaction ก่อนเพิ่ม Used Days
  R024 | BR-24 | Employee Code และ Email ต้องไม่ซ้ำ และข้อมูลอ้างอิง Department, Position และ Supervisor ต้องถูกต้อง
  R025 | BR-25 | Department Name และ Position Name ต้องมีความยาว 2 ถึง 100 ตัวอักษรและไม่ซ้ำโดยไม่คำนึงถึงตัวพิมพ์
  R026 | BR-26 | Leave Type Code ต้องเป็นตัวพิมพ์ใหญ่หรือตัวเลข 2 ถึง 10 ตัว และ Code กับ Name ต้องไม่ซ้ำ
  R027 | BR-27 | Holiday Date ต้องไม่ซ้ำ และข้อมูล Name, Type, Description และ Status ต้องผ่านการตรวจสอบ
  R028 | BR-28 | Leave Entitlement ต้องไม่ซ้ำในชุด Employee, Leave Type และ Year โดย Year อยู่ระหว่าง 2000 ถึง 2100 และ Total/Used Days อยู่ระหว่าง 0 ถึง 365
  R029 | BR-29 | Username ต้องไม่ซ้ำ มีความยาว 4 ถึง 50 ตัว และใช้ตัวพิมพ์เล็ก ตัวเลข จุด ขีดล่าง หรือขีดกลางตามรูปแบบที่กำหนด
  R030 | BR-30 | User Account หนึ่งรายการผูกกับ Employee หนึ่งรายที่ยังไม่มีบัญชี Role ต้อง Active และสถานะบัญชีต้องเป็น Active, Inactive หรือ Locked
  R031 | BR-31 | Admin Create หรือ Reset Password ต้องสร้าง Temporary Password และบังคับให้ผู้ใช้เปลี่ยน Password โดยบัญชี Inactive ไม่สามารถ Reset Password ได้
  R032 | BR-32 | Password ใหม่ต้องมีอย่างน้อย 10 ตัวอักษร มีตัวพิมพ์ใหญ่ ตัวพิมพ์เล็ก ตัวเลข อักขระพิเศษ ไม่มีช่องว่าง และไม่เท่ากับ Username, Email หรือ Password เดิม
  R033 | BR-33 | Profile Image รองรับ JPEG, PNG หรือ WebP หนึ่งไฟล์ ขนาดไม่เกิน 2 MB และเนื้อหาไฟล์ต้องตรงกับชนิดไฟล์
  R034 | BR-34 | Notification List, Read และ Delete ต้องจำกัดด้วย User ของ Session
  R035 | BR-35 | Protected Function ต้องปฏิเสธบัญชีที่ไม่ Active และ Session ที่หมดอายุหรือ Token Version ไม่ตรง
  R036 | BR-36 | OTP เป็นตัวเลข 6 หลัก มีอายุเริ่มต้น 5 นาที ตรวจผิดได้สูงสุด 5 ครั้ง มีระยะรอขอใหม่และจำกัดจำนวนการขอในช่วงเวลา
  R037 | BR-37 | Reset Token มีอายุเริ่มต้น 15 นาที ใช้ได้ครั้งเดียว และเมื่อ Reset สำเร็จต้องยกเลิก Token และ OTP อื่นที่ยังใช้ได้ของผู้ใช้รายนั้น

  R003 | NFR-03 | Password และ Temporary Password ต้องจัดเก็บเป็น Hash ส่วน OTP และ Reset Token ต้องไม่จัดเก็บเป็น Plain Text
  R004 | NFR-04 | Backend ต้องบังคับ Role และ Data Scope ของทุก Endpoint สำคัญ แม้มีการเรียก Direct API
  R005 | NFR-05 | ข้อมูลธุรกิจหลักต้องใช้ Backend API และฐานข้อมูลกลางเป็น Source of Truth เดียวกัน
  R006 | NFR-06 | กระบวนการ Submit, Approve, Reject และ Password Reset ที่เปลี่ยนหลายข้อมูลต้องทำงานแบบ Transaction
  R007 | NFR-07 | Backend ต้องตรวจ Required Field, รูปแบบข้อมูล, ช่วงค่า, Duplicate และ Reference ก่อนบันทึก
  R008 | NFR-08 | การ Upload ต้องจำกัดจำนวน ขนาด และชนิดไฟล์ พร้อมตรวจสิทธิ์เข้าถึงไฟล์
  R009 | NFR-09 | ระบบต้องแสดง Error Message ที่เข้าใจได้และไม่เปิดเผยข้อมูลบัญชีหรือรายละเอียดภายในที่ไม่ควรเปิดเผย
  R010 | NFR-10 | ระบบต้องรองรับ Responsive Web และ Function หลักต้องใช้งานได้บน Desktop และ Mobile ขนาด 390 x 844
  R011 | NFR-11 | Interactive Control สำคัญ โดยเฉพาะ Icon-only Action ต้องมี Accessible Name และรองรับ Focus
  R012 | NFR-12 | Event ด้าน Security และ Approval ที่ระบบกำหนดต้องมีข้อมูลผู้กระทำ Action, Record, Result และ Metadata เพื่อการตรวจสอบย้อนหลัง
